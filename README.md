# ITMO 2026 — группа 2: виртуальные машины и сеть

Ansible создаёт KVM/libvirt-стенд из 5 ВМ Debian 13: три совмещённых узла по 4 ГиБ (на каждом предусмотрены два экземпляра ClickHouse и один ZooKeeper), маршрутизатор и генератор нагрузки. Три ДЦ представлены отдельными Linux-мостами. Реплики одного шарда размещены в разных ДЦ.

Задание: https://github.com/Ravino/devops_education/tree/main/itmo-sysadm-2026

Новая схема подготовлена только в коде и на действующий сервер не применена.
Это выбранное командой отклонение от исходной схемы задания с 11 ВМ.
Плейбук готовит инфраструктуру, а не устанавливает и не переносит сервисы.

## Запуск

Контроллер: Linux, Python 3.11+, OpenSSH, openssl. Гипервизор: Debian/Ubuntu amd64, `/dev/kvm`, sudo/root, доступ в интернет. Гостевые ОС всегда Debian 13. Установку пакетов и настройку libvirt выполняет Ansible.

```bash
cd ~/ucheba/sis_admin
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
# Проверьте inventory/hosts.yml. В keys/team/ находятся пять публичных ключей.
# Загрузите свой соответствующий закрытый ключ в ssh-agent.
.venv/bin/ansible-playbook site.yml
.venv/bin/ansible-playbook verify.yml
```

По умолчанию используется разрешённый тестовый сервер `178.237.199.16`, пользователь root. На текущем контроллере доступ по SSH-ключу уже работает. Пароль сервера не хранится в проекте. Для другого сервера измените inventory; при парольной аутентификации добавьте `--ask-pass` и при необходимости `--ask-become-pass`. Не отключайте проверку SSH host key.

Пять ключей команды заданы в `keys/team/`, доступ не зависит от компьютера,
с которого запускается Ansible. `lab_public_key_file` по умолчанию пустой;
`-e lab_public_key_file=/путь/key.pub` добавляет необязательный ключ оператора.
Закрытый ключ загрузите в `ssh-agent` (`ssh-add /путь/key`) для обоих SSH-переходов.
Подробнее: [доступ команды](docs/ssh-access.md).

## Что создаётся

- Роли `hypervisor`, `vm`, `router`, `guest`; Ansible Collections не требуются.
- Четыре сети libvirt: WAN с NAT и три L2-моста ДЦ без адресов гипервизора.
- ВМ из фиксированного официального cloud-образа Debian с проверкой SHA-512, NoCloud и статическими MAC/IP.
- 24 пустых диска для RAID, гостевой агент QEMU, сетевые инструменты, chrony и временный `/etc/hosts`.
- Маршрутизация и firewall на router; ограничение портов ZooKeeper 2181/2888/3888.
- Технический пользователь `ansible` для автоматизации, SSH только по ключу; аварийный пароль только для консоли.
- `inventory/guests.generated.yml` для участников команды: группы clickhouse/zookeeper/load/router, IP, zookeeper_id и список clickhouse_instances с shard, replica, raid_level, портами и дисками каждого экземпляра.
- Скрипты сетевых экспериментов с таймером отката и журналированием; отдельные точки входа `scripts/{wan,isolate-zk,asymmetric,mtu,switch,dc,two-dc}.sh` запускаются на соответствующей целевой машине.

[IP-план и схема](docs/ip-plan.md), [ранбуки](docs/runbooks.md), [результаты проверки](docs/validation.md), [журнал ИИ](docs/ai-log.md).

Сервисы ClickHouse, ZooKeeper, генератор нагрузки, RAID/LVM/XFS, SSSD и агенты мониторинга здесь не устанавливаются: для них подготовлены ВМ и inventory. Корпоративный вход пользователей подключает группа 3; техническая учётная запись не заменяет SSSD.

## Ресурсы и ограничения

Профиль: три узла по 4096 МиБ и 2 vCPU, router и load — по 512 МиБ и 1 vCPU. Всего 13 ГиБ RAM и 8 виртуальных CPU. На сервере с 16 ГиБ остаётся примерно 3 ГиБ для хоста и накладных расходов. Два ClickHouse, ZooKeeper и ОС делят 4 ГиБ; это не гарантия 2 ГиБ каждому ClickHouse. Плейбук проверяет резерв хоста минимум 2 ГиБ.

Диски qcow2 разреженные: 120 ГиБ логического пространства под RAID плюс корневые диски. На тестовом сервере около 85 ГиБ было свободно до установки, поэтому полностью заполнить все виртуальные диски нельзя. Для нагрузочных/дисковых сценариев нужен больший физический том; следите за `df -h /var/lib/libvirt/images`. Удаление гостевых файлов само по себе не гарантирует возврат места qcow2.

Три ДЦ моделируются на одном физическом хосте: его отказ уничтожает доступность всего стенда. Это учебная модель доменов отказа.

Повторный `site.yml` сохраняет существующие диски, восстанавливает включение/автозапуск ВМ и применяет гостевые роли. Cloud-init сеть и seed задаются при создании. Изменение сети требует пересоздания соответствующей ВМ; ключи команды обновляются ролью ssh_access и отдельным access.yml без пересоздания; объём существующих дисков автоматически не меняется. Изменённый XML ВМ вступает в силу после её выключения и запуска. Изменять сеть уже созданных ВМ одним изменением YAML нельзя. Изменение существующих сетей останавливается до применения.

## Пересоздание и удаление

Если существуют старые домены `g2-*`, отсутствующие в новом `lab_vms`,
`site.yml` и `destroy.yml` остановятся до изменения инфраструктуры. Это предотвращает
одновременный запуск старых и новых ВМ сверх бюджета памяти и потерю старых данных.
Миграция сервисов выполняется отдельно. Старый список ВМ сохранён в
`profiles/legacy-11-vms.yml`; он не используется по умолчанию.

Следующая команда **уничтожает диски ВМ текущего `lab_vms`** и создаёт их заново:

```bash
.venv/bin/ansible-playbook rebuild.yml -e confirm_destroy=itmo-g2
```

Только удалить стенд: `ansible-playbook destroy.yml -e confirm_destroy=itmo-g2`. Пакеты libvirt, общий базовый образ, каталоги отсутствующих в lab_vms ВМ и сторонние службы остаются. После пересоздания проверьте новые SSH host keys через консоль и удалите только прежние записи соответствующих гостевых IP с `ssh-keygen -R <IP>`; автоматическое принятие изменённых ключей намеренно запрещено.

`--check` не является полноценной проверкой на пустом сервере: virsh и создаваемые файлы ещё отсутствуют. Используйте syntax-check/lint и реальное развёртывание на тестовом гипервизоре.

## Репозиторий

Публичный репозиторий: [pepe1az/sis_admin](https://github.com/pepe1az/sis_admin), ветка `main`.
`.local/` (в том числе пароль консоли и локальная авторизация GitHub), `.venv/`,
приватные ключи и образы дисков исключены из Git.

```bash
git clone https://github.com/pepe1az/sis_admin.git
cd sis_admin
```

На исходном компьютере автора имя и email для коммитов заданы только в этом
репозитории. Push использует HTTPS и отдельную авторизацию `pepe1az` в
игнорируемом каталоге `.local/gh`; глобальные настройки рабочего аккаунта и
его SSH-ключи не менялись. Эти настройки не передаются при клонировании:
каждый участник использует собственный аккаунт и доступ к GitHub.

Сценарий №13: `g2-chaos two-dc --dc dc2 --peer dc3 --seconds 120` на гипервизоре.
Для проверки только нового сценария: `.venv/bin/ansible-playbook smoke-two-dc.yml`.
