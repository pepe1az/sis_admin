# Проверка интеграции ClickHouse

Дата: 2026-11-14. Проверка выполнялась не на общем стенде KVM, а на локальной
копии шести ВМ: шесть контейнеров Debian 13 (systemd + SSH) с адресами
`172.31.29.11–16`, по одному инстансу ClickHouse на контейнер и Keeper на
`.11`, `.13`, `.15` (по одному на ДЦ). Использовался тот же плейбук
`clickhouse.yml`, что и для стенда `sis_admin`; отличия — только адреса,
лимиты памяти и пароль лаборатории.

## Команды

```bash
ansible-playbook clickhouse.yml \
  -i .cache/integration/inventory.yml
ansible-playbook clickhouse.yml \
  -i .cache/integration/inventory.yml          # повторно, идемпотентность
ansible-playbook clickhouse-verify.yml \
  -i .cache/integration/inventory.yml
```

Проверка firewall выполнялась из одноразового контейнера вне allow-list
(`172.31.29.30`) и с соседнего узла ClickHouse (`172.31.29.12`).

## Результаты

### Развёртывание

`PLAY RECAP`, первый запуск:

```
g2-ch1r1 : ok=58 changed=34 unreachable=0 failed=0
g2-ch1r2 : ok=36 changed=22 unreachable=0 failed=0
g2-ch2r1 : ok=43 changed=26 unreachable=0 failed=0
g2-ch2r2 : ok=36 changed=22 unreachable=0 failed=0
g2-ch3r1 : ok=43 changed=26 unreachable=0 failed=0
g2-ch3r2 : ok=36 changed=22 unreachable=0 failed=0
```

Повторный запуск: на всех шести узлах `changed=0, failed=0`. Идемпотентность
подтверждена.

### Кластер

`system.clusters` на каждом узле содержит 6 записей, по две на шард:

```
shard 1: 172.31.29.11:9000, 172.31.29.12:9000
shard 2: 172.31.29.13:9000, 172.31.29.14:9000
shard 3: 172.31.29.16:9000, 172.31.29.15:9000
```

Keeper: один лидер (`172.31.29.13`) и два фолловера, `ruok` → `imok`,
`mntr`/`srvr` отвечают, `conf` не выполняется.

Схема: `bench.events_local` (`ReplicatedMergeTree`) и `bench.events`
(`Distributed`) созданы на всех шести узлах, у каждой локальной таблицы
`total_replicas=active_replicas=2`.

Вставка 500 строк в `bench.events` дала 1000 копий в локальных таблицах
(500 × 2 реплики). Генератор нагрузки на `g2-ch1r1` выполняет `INSERT` и
аналитические запросы; `system.query_log` подтверждает `GROUP BY`.

### Отказ реплики

Вручную остановлен `clickhouse-server@ch1` на `g2-ch2r2` (шард 2, dc3).
Вставка в `bench.events` продолжилась, после запуска реплика догнала данные,
`active_replicas` вернулось к 2. Это проверка репликации, а не полный сценарий
отказа ДЦ.

### Firewall

С узла вне allow-list (`172.31.29.30`) порты 9000, 8123, 9181, 9234, 9363,
9365 закрыты. С соседнего узла ClickHouse (`172.31.29.12`) те же порты
открыты. `ping` между узлами работает, ICMP не блокируется, `ufw` не
устанавливается.

## Ограничения проверки

- Это не проверка на реальном KVM-стенде `sis_admin`: сеть, ProxyJump,
  ресурсы и нагрузка на общем стенде отличаются. Перед приёмкой нужно
  прогнать `clickhouse.yml` и `clickhouse-verify.yml` на стенде группы.
- В контейнерах меньшие лимиты памяти (400 МиБ на инстанс), поэтому проверка
  не измеряет производительность и p95 запросов.
- Полный отказ ВМ/ДЦ не выполнялся: проверялся только отказ одной реплики.
  Для стенда остаются сценарии `two-dc` и общая матрица отказов.
- Docker-лаборатория в репозиторий не добавлена: она использовалась только
  как временный полигон. Для воспроизведения достаточно создать шесть ВМ
  Debian 13 и заполнить inventory по образцу `inventory/guests.generated.yml`.
