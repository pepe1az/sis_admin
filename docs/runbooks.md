# Эксплуатация и сетевые сценарии

## Подключение и восстановление

```bash
ssh -J root@178.237.199.16 ansible@10.22.1.11
ssh root@178.237.199.16
virsh list --all
virsh console g2-ch1r1
# Выйти из console: Ctrl+]
```

В консоли входите как `ansible`; аварийный пароль находится на контроллере в `.local/console-password` (режим 0600, каталог 0700). После входа доступен `sudo`. Не добавляйте `.local` в Git. Пароль через SSH отключён. Пароль консоли устанавливается гостевой ролью после первого SSH-подключения.

При недоступной сети проверьте `ip -br a`, `ip r`, `systemctl status networking`, `nft list ruleset`, `journalctl -b`. На гипервизоре проверьте мосты и `systemctl status itmo-g2-routes`. Для диагностирования первого запуска используйте `virsh console`, журналы `/var/log/libvirt/qemu/`, при необходимости подключите root-диск к отдельной rescue-ВМ.

## Сценарии

`g2-chaos` установлен на хосте и ВМ. Таймер `systemd-run` регистрируется **до** нарушения связи. Время — 10–600 секунд. Состояние сохраняется в `/var/lib/itmo-g2-chaos/active.json`, журнал — `/var/log/itmo-g2-chaos.log`, результат отката также в journald. Одновременно разрешён один эксперимент на машине. При перезагрузке `itmo-g2-chaos-recovery.service` восстанавливает оставшееся состояние. Если откат завершился ошибкой, transient service повторяет его через 5 секунд; всё равно контролируйте журнал и итоговую связность.

Перед запуском: `ansible-playbook verify.yml`, работающая консоль, сбор метрик группой 1. Не запускайте развёртывание или перезагрузку служб firewall во время эксперимента. Откат восстанавливает инфраструктуру, но не гарантирует сохранность прикладных данных после жёсткого выключения.

### 8. Деградация WAN (на g2-router)

```bash
sudo g2-chaos wan --dc dc1 --delay 100 --loss 2 --corrupt 0.1 --reorder 1 --seconds 120
sudo tc -s qdisc show dev dc1
sudo tc -s filter show dev dc1 parent 1:
```

Воздействие применяется к выходящему трафику **из других ДЦ в dc1**. Трафик управления от `172.30.2.1` не попадает под netem. Задержка 50–300 мс, jitter 10 мс, параметры потерь/повреждения/перестановки 0–10 %. Для обратного направления выполняйте отдельный эксперимент на другом интерфейсе после завершения первого. Это направленная деградация; для RTT эффект измеряется ping между ДЦ.

### 9. Изоляция ClickHouse от ZooKeeper (на выбранной ClickHouse ВМ)

```bash
# На g2-ch1r1:
sudo g2-chaos isolate-zk --node 10.22.1.11 --seconds 120
sudo nft list table inet g2_chaos
```

Блокируются исходящие соединения к tcp/2181 всех трёх ZooKeeper и ответы от них, включая уже установленные сессии. Выполнение на самом узле необходимо: трафик к ZooKeeper в том же ДЦ через router не проходит. Клиентские порты ClickHouse не блокируются.

### 10. Асимметричный разрыв и MTU (на g2-router, отдельно)

```bash
sudo g2-chaos asymmetric --dc dc1 --peer dc2 --seconds 120
# После отката:
sudo g2-chaos mtu --dc dc1 --seconds 120
# На узле другого ДЦ:
ping -M do -s 1400 -c 3 10.22.1.11
```

Асимметрия блокирует пакеты dc1 → dc2, включая ответы. Это односторонний сетевой drop; TCP при нём обычно не работает в обоих направлениях. MTU уменьшается до 576 на интерфейсе dc1, ICMP fragmentation-needed подавляется — моделируется чёрная дыра PMTUD. Небольшой ICMP/SSH может продолжать работать.

### 11. Отказ коммутатора (на гипервизоре)

```bash
sudo g2-chaos switch --dc dc2 --seconds 60
ip -br link show virbr-g2dc2
```

Опускается только мост указанного ДЦ. Публичный интерфейс хоста не затрагивается. После таймера мост поднимается.

### 12. Отказ целого ДЦ (на гипервизоре)

```bash
sudo g2-chaos dc --dc dc2 --seconds 60
virsh list --all
```

`virsh destroy` жёстко выключает только запущенные ВМ этого ДЦ. Их диски сохраняются. После таймера запускаются именно те ВМ, которые работали перед экспериментом. Router продолжает работать. Для dc1 также выключается генератор нагрузки — это нужно учитывать при измерении ошибок, либо запускать внешний генератор.

### 13. Отказ двух ДЦ (на гипервизоре)

```bash
sudo g2-chaos two-dc --dc dc2 --peer dc3 --seconds 120
virsh list --all
# Отдельная точка входа из репозитория на гипервизоре:
sh scripts/two-dc.sh --dc dc2 --peer dc3 --seconds 120
```

ДЦ должны различаться. Выключаются только работающие ВМ выбранной пары;
маршрутизатор, третий ДЦ и посторонние ВМ не затрагиваются. ВМ, выключенные
до эксперимента, остаются выключенными и после отката. Один таймер на гипервизоре
восстанавливает обе площадки. При ошибке во время выключения выполняется
немедленный откат; таймер остаётся дополнительной защитой.

Гипотеза для будущего полного кластера: остаётся один ZooKeeper из трёх,
кворума нет; один шард полностью недоступен, у двух других остаётся по реплике.
Для dc2 + dc3 остаются ch1r1 и ch3r2 в dc1, обе реплики шарда 2 выключены.
Поведение вставок, чтения и восстановления нужно измерить на работающем
ClickHouse/ZooKeeper, затем сверить данные между репликами.
При выборе dc1 выключается также генератор нагрузки: измерения в таком случае
должны выполняться извне отключаемых ДЦ.

Проверка инфраструктуры: `.venv/bin/ansible-playbook smoke-two-dc.yml`.
Она вводит реальный отказ dc2 + dc3 на 30 секунд, проверяет точный список
оставшихся ВМ, автоматическое восстановление и SSH. Проверка кворума и данных
в этот плейбук не входит.

### Ручной откат

На машине, где запущен эксперимент:

```bash
sudo g2-chaos rollback
systemctl list-timers 'g2-rollback-*'
tail -30 /var/log/itmo-g2-chaos.log
```

Старый таймер не откатит новый эксперимент: таймер связан с ID своего запуска. При ручном аварийном вмешательстве:

- netem: `tc qdisc del dev dc1 root` (только на router и только созданный `handle 1:`).
- nft: `nft delete table inet g2_chaos` (не трогать `g2_router`, `g2_nat`, `g2_zookeeper`).
- MTU: `ip link set dc1 mtu 1500`, затем удалить `g2_chaos`.
- мост: `ip link set virbr-g2dc2 up` на хосте.
- ВМ: `virsh start <имя>` на хосте согласно списку `undo` в active.json.

После каждого сценария запускайте `verify.yml`. Ответственные за ClickHouse/ZooKeeper дополнительно проверяют readonly, очередь/задержку репликации, кворум и число строк; сетевой ping этого не доказывает.

## Интеграция

Группе 1 передайте `inventory/guests.generated.yml` и IP-план. Добавьте реальные IP мониторинга в `lab_monitoring_sources` для доступа к tcp/2181. Порты exporter согласуйте с владельцами сервисов.

Группе 3 передайте DNS-записи и подсети. Укажите корпоративные DNS в `lab_dns` **до создания** ВМ; для уже созданных меняйте конфигурацию резолвера отдельной ролью. Подключите их chrony/SSSD/CA. Межгрупповой VPN/маршрут требует адресов, peer keys и подсетей другой стороны; их нельзя определить из задания. Публичного доступа ко всем портам ВМ по умолчанию нет. После согласования добавьте точечные маршруты и разрешения на router.
